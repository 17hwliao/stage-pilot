# 统一 Review 流程

只在用户要求 Review、审计、修复复核，或已经选择阶段 Review 时使用。直接要求已构成相应授权，不再问是否开始。阶段验收核对不等于 Review。stage-pilot 负责阶段与交接，本页是审查的唯一流程源；可用的 Review skill 复用本页，不重复审查。

## 范围与写入边界

- **stage（默认）**：本阶段更新的内容；包含暂存、未暂存和新增文件，必要时沿真实调用链延伸到共享契约与边界。既有无关改动排除。缺少可信基线时只审查可确认文件，不把整个 main 差异算成本阶段。
- **full（明确要求全量、整个项目）**：读取[全量范围](review-full.md)，按主要模块及调用关系覆盖项目。没有明确扩大范围时，不把普通“审计”或发现一个疑点自动升级为全量。
- **修复后复核**：沿用上轮问题、范围和修复 diff，直接使用[定向复核](review-followup.md)；不是再执行本页的完整初评，也不是第三种范围。
- 本地默认 Review 包含已确认缺陷的范围内最小修复与定向复核；只读、仅方案、先设计后实施等现行限制优先。已有明确修复授权直接沿用。可选重构、新功能、公共接口或数据迁移不因 Review 自动获准；先把方案准备具体，在真实授权边界处停止。

## 初评：六步，不强制输出六份文档

1. **前置准备。** 核对实际目录、分支与工作区，复用阶段需求、项目约定、历史问题和仍适用的验证结果。固定本次范围及基线；已有问题清单沿用编号。无 Git 时按已知文件版本判断。仅补问无法推断且影响结论的缺项。
2. **分层评审。** 从用户行为／入口，到模块职责与调用契约，再到实现和数据流。stage 从 diff 出发，full 从主要功能路径出发；按疑点读取必要调用方，避免只看局部函数，也不为了形式读遍所有文件。
3. **专项检查。** 只选适用项：输入／输出与兼容性、权限与敏感信息、状态所有权与并发、资源释放与失败恢复、重复事件和幂等、配置及缓存一致性、测试是否验证真实行为。性能判断依据实际热点或测量，不做假想优化。用项目惯例识别多余抽象、类型绕过、重复状态及冗余注释；保留有契约依据的防御与抽象。
4. **风险汇总。** 给候选问题稳定编号，列位置、触发条件、影响、调用／数据路径、证据与优先级。区分确定缺陷、待证实疑点、可选整理；合并同根因，不凑数。无可确认问题也如实报告。
5. **输出修复方案。** 对应问题编号说明根因、最小改动、受影响调用方、边界与少量必要测试。复杂改动先在已有载体或进度中给出方案；小改可用几句话，不为每个步骤另建文档或等待一次确认。内部代码整理按已观察到的冲突或维护成本提议，默认不顺带实施。
6. **二次核实是否真实存在。** 动手前重读具体代码、调用方、配置和旧记录，核对可达性、是否已修复、契约是否允许该行为。可用最小复现或行为测试证伪；不能复现且证据不足的降为待核实，误报撤回，不通过添加兜底“修复”不存在的问题。复现、静态判断和实际测试分开。

## 修复与复核

确认缺陷后，在当前授权内实施最小修复，保持无关行为和现有工作；从根因补齐必要边界，不只遮盖症状。先保留原问题与预期行为的依据。若只有方案授权，交付方案和验证方法，不能声称已修复。

完成修改后使用[定向复核](review-followup.md)：逐项检查旧问题是否解决、修复是否带来新风险、边界是否补全、相关少量必要自动测试结果，并给出最终结论。重点风险必须重扫，但不重新完整全量审查。只有新证据表明影响越过原范围，才沿相关路径扩查并说明理由。

## 交付与记录

- 最终先给结论：**本次范围修复并复核通过／部分完成，仍有问题或验证缺口／只读审查或方案已完成，未实施**。有重大未解决风险时明确不能据此判定就绪；测试通过不等于整个项目安全或所有需求验收完成。
- 复用一份简短问题清单：编号、根因及位置、最终状态、修复摘要、复核／测试证据、剩余风险。状态可用“已修复并验证／已改待验证／仍存在／证据不足／误报撤回／原已修复”。缺陷条目完整报告，建议不凑数。
- 说明 stage/full、实际覆盖路径、未覆盖部分。全量增加必要的模块调用／冲突摘要；普通 Review 只给阶段相关的少量补全或整理建议。按需参考[next-steps.md](next-steps.md)，不重复再跑一次评估。
- 有项目现成载体时更新其中一小节；轻量任务可直接回复。已有匹配阶段时，直接要求审查、范围切换或修复复核用[状态接口](stage-state.md)的 review-start 记录本轮明确授权，不重新回答旧 offer；followup:true 标识定向复核，沿用旧范围而不重跑初评。只有阶段选项的首次响应才用 choose。无登记阶段不制造阶段。
- 完成后登记 review-result：经 review-start 发起须带同 request_id，mode 匹配已授权 stage/full，summary 记录结论、未解决项及证据位置；verified=true 仅表示确实完成这轮流程，不表示所有问题通过。中途 Review 不替代开发验收，既有“先 Review 后交接”的意图也不因范围切换丢失；不用伪造完成、重新开阶段或旧回执来绕过状态。
- 一轮修复与定向复核后，剩余已授权问题继续做有证据的小步修正；没有新改动、新失败或具体未解决证据时停止，不循环扫描至“零问题”。完整交接仅沿用已有授权，携带真实问题状态，不重新询问。

默认由当前代理执行，不联网、不派生代理、不回读全聊天。仅为核实具体问题运行相关检查；联网核实、代理协作或外部操作按实际任务需要和授权使用。审查本身不授权发布或远程写入。
