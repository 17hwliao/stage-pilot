# 修复后定向复核

适用于“修一下这些问题”“核对旧问题修好了没”“复核刚才的修复”；即使来源是全量 Review，本次仍是定向复核。沿用原问题编号、触发条件、验收预期和修复基线，不从头建立全项目问题清单。

已有匹配阶段时，用户新要求的复核用 review-start、followup:true 和新 request_id 登记，mode 沿用原范围；回传同编号的 review-result，保留旧结果。没有登记阶段时直接在原载体记录。一次已授权 Review 内的修复复核仍属于同一请求，不额外调用 review-start，也不重新索要授权。

## 复核范围

检查修复 diff、直接调用方／被调用方、共享状态及其受影响入口。涉及权限、数据完整性、并发、兼容性或资源生命周期等重点风险时，沿相关路径重扫；说明路径与依据。发现新风险在同一清单补记来源，只有真实影响扩散才扩大范围。

逐项回答：

1. **旧问题修好了吗？** 对照原复现与根因，核实关键行为已经改变；仅文件变动、编译成功或“上轮已处理”不能证明。原本就是误报或已有修复时说明依据，不再次改代码。
2. **新坑出现了吗？** 检查修复对其他调用方、异常路径、状态写入、重试／取消、资源释放、权限及存储契约的影响；重点风险重扫，不用扩大到不相关模块来替代。
3. **边界补全了吗？** 从实际契约选择正常路径、原失败条件和最相关的空值／无效值／重复事件／并发或失败恢复条件；避免机械枚举所有理论边界。
4. **少量必要测试能证明什么？** 优先复用相关测试；缺少回归保护时补能在旧实现失败、修复后通过的行为测试，预期来自需求或独立例子。测试数量按风险决定，不设固定配额。只运行原问题、受影响调用契约及必要边界；共享基础设施改动确需更广检查时说明理由。保护用户工作，验证旧实现优先用临时副本，不回滚真实工作区。
5. **最终结论是什么？** 按问题登记已修复并验证、已改待验证、仍存在、证据不足或误报撤回；列实际命令和结果、未覆盖条件、残余风险。证据不足不写“全部修好”，没有剩余证据就结束。

少量必要测试指能自动验证相关行为的检查，不等于要求用户补做手动或实机体验；遵守当前用户的测试收尾决定。跳过的验证写清楚，不能包装成通过。测试环境不可用时保留修复与限制，不能反复生成更多候选碰运气。

复核仅针对相关问题闭环；不重新跑全部六步初评，不每修一次就全量审查、生成新阶段或新问题报告。继续修复仅由新的具体失败或未解决问题驱动，公共契约变更、迁移和可选重构仍遵守实际授权边界。
